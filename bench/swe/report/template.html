ModelFabric benchmark · SWE-bench Verified · three nodes · 2026-09-24

Scheduling did not make the median call faster. It removed the tail.

Qwen3.8-27B on three heterogeneous engines, the same 20 SWE-bench Verified tasks run twice: once with a plain balancer by in-flight request count across the engines, once through llm-d's tuned profile. The median model call was marginally faster without a scheduler. Everything else went the other way — tuned finished the set in 64 minutes against 119, re-prefilled 4.4× fewer tokens, and cut the worst single call from 39 minutes to 7. Resolve rate did not separate the two, and at twenty tasks it cannot.

helion prefills roughly 10× slower than the 5090, so the same request costs ten times as much there. A balancer by request count cannot know that, so under direct both GPUs idle about a quarter of the time while the Mac stays pinned, and the set finishes at the Mac's pace. Under tuned all three sit at 83% or above and the queue depth is deliberately parked on helion: the scheduler is choosing to keep 1.61 requests waiting on the slow node so the fast ones never starve.

That choice has a cost we did not set out to measure. llm-d's room filter counts a free slot as a free slot regardless of what the engine behind it can do, so the slowest engine looks available longest and ends up the most oversubscribed in the fleet. helion's decode fell to 11.2 tok/s under tuned. A filter that weighted a slot by the engine's measured rate would place that queue differently — that is the next thing to test, not a settled result.

Read these numbers with care

  • The resolve rates do not support a conclusion. 17/20 against 15/20 looks like a win for tuned and is not one: only 13 tasks resolved under both. tuned uniquely solved four, direct uniquely solved two, so six of twenty flipped. At temperature 1.0 and n=20 that is sampling, and a 2-task gap sits inside it. Routing shows in prefill volume and latency; on correctness this run says nothing.
  • The empty patches are context exhaustion, not timeouts. All three exited ContextWindowExceededError at a peak context around 130,900 of the 131,072-token pool; the 100-step cap and the 2-hour sandbox limit were never reached. astropy-13398 failed this way in both modes (58 turns under tuned, 74 under direct) and is excluded. astropy-14598 is the one to watch rather than to cite: tuned submitted it in 40 turns at a peak of 87k, direct took 80 turns and hit the ceiling. Turn count is the agent's own path at temperature 1.0, so a single instance proves nothing — but it is the mechanism by which routing could cost a solve and not merely time.
  • The two modes ran back to back, not interleaved. tuned ran 15:29–16:33 and direct 16:33–18:33 on a freshly reloaded fleet each time. Anything that drifted over those four hours — thermals, other load on the tailnet — lands on direct. Alternating the order is the check, and has not been run.
  • The engines were loaded text-only, and need not have been. Both arms ran -vision off, on the understanding that llama.cpp could not draft a prompt carrying an image and so a model with its projector loaded lost MTP speculation and its 2× decode. Re-tested on 2026-09-24 with the same context and slot count plus the projector, two concurrent image requests succeeded with drafting live throughout — the defect is gone from the builds this fleet runs. Both arms used identical settings, so nothing here is invalidated; the flag simply bought nothing, and the next run drops it.
  • Prefill calibration is the one input that leaks between modes. llm-d schedules against a peak-prefill figure ModelFabric measures and saves; it drifted 2000 → 1010 → 1192 → 880 → 628 → 614 tok/s across runs. This pair used 614. Pin SWE_PEAK_PREFILL to compare across days.
  • Two cache figures, two denominators. The table's 97.4% / 90.2% come from the agent's own per-call usage. The engines' lifetime counters gave 84.8% for direct, because they also count health probes and reset on reload. The per-call figure is the one to quote; the engine counters are what attribute work per node.

What this run asks for next

  • queued Aider polyglot on the same fleet. These tasks reuse 97% of their prompt, so this benchmark mostly measures prefix affinity. Polyglot's exercises start cold, which tests placement instead. A profile that wins both is better than one that wins here.
  • queued Reduced reasoning effort. 98% of the output on these tasks is reasoning. Whether that buys the resolve rate is a separate question this pair does not answer.
  • queued Reverse the order. direct first, then tuned, to rule out drift over the four-hour window.
  • open Weight a slot by the engine behind it. The room filter treats helion's slot as worth a 5090's, which is why the slow node carries the deepest queue.

Every mode reloads all three engines first, so none inherits another's caches — which also means the engines' lifetime counters must be read before the next reload wipes them.
